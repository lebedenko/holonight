# Private cache-before-pixels diagnostic preparation

This package asks whether the existing offscreen startup harness can accept validated
pixels while disk-cache storage remains outstanding. It authorizes preparation only.
Success is **prepared; native correctness and execution capability unvalidated**.
No production source, public API, submodule pin, installed binary or sealed historical
evidence changes. Streaming and validation reuse remain **Deferred**, overall candidate
selection **Evidence insufficient**, and historical qualification **78/80**.

## Evidence and package boundary

The [read-only evidence tool](../../scripts/preview-cache-publication-evidence.py) pins
the committed [critical-path review](startup-critical-path-review.md), accepted helper,
remainder, applicability and identity evidence through the existing retained provenance
chain, and the completed streaming findings, consumed hashes, inventories and passing
preparation/build/execution verification bindings. Input discrepancies stop preparation;
they are never repaired. Current checkout bytes provide comparison context in the review
only. They do not supply the private variants or establish loading identities.

The [preparer](../../scripts/prepare-preview-cache-publication.py) accepts only `--output`
for a fresh direct child of ignored `build/` named `preview-cache-publication-*`.
Collisions, overlapping paths and symlink escapes fail before mutation. There is no
build, staging or execution interface. Complete retained qualification C sources,
corrected shared harness and retained `3200x2400.png` are copied using historical source,
harness and fixture manifests. Both variants receive identical diagnostic instrumentation.
Only early progressive publication differs. Packages retain complete inventories, exact
literal anchors, private diffs, protocol, tools, consumed identities and assessment.
Inputs are rechecked after preparation. Both prepared and blocked outputs are sealed.
A seal records complete file membership; it does not make a blocked result acceptable.

The control keeps the existing publication order. The early variant copies the
progressive result after successful transaction return and the existing successful
original-decode, valid-tier and unchanged-source checks, immediately before `storeRaster()`.
It checks cancellation before publication, preserves the original image for storage,
and suppresses only that later duplicate progressive publication. Other publication
paths retain their existing ordering. Storage, EXIF formatting, memory-cache insertion
and final publication remain on the existing worker path. Cancellation checkpoints,
stale-generation rejection, timeout/shutdown behavior, private atomic cache writes and
session cleanup remain intact. No storage thread, launcher/protocol change, SVG work
or warm-cache optimization is included.

## Frozen observation contract for a later task

The protocol freezes two excluded warm-ups, control then early, followed by five pairs:
control/early, early/control, control/early, early/control, control/early. This is exactly
**10 diagnostic observations plus two warm-ups**, one observation per fresh process,
with the existing cold `startup` scenario, 256×256 request, offscreen Qt, private source
and cache copies. No retries, replacement observations, cache flushing, affinity changes
or artificial load are allowed. The workload deadline remains 30 seconds and process,
descriptor and scope cleanup share one five-second budget. Later staging/removal must
retain the existing ownership, collision, protected-generation lease and conservative
cleanup checks. No execution commands are prepared in this iteration.

Private instrumentation emits `CACHE_PUBLICATION` JSON records using `CLOCK_MONOTONIC`
nanoseconds (serialized as decimal strings; a later collector must parse them as integers).
The future controller must set a unique nonempty `HOLONIGHT_CACHE_INVOCATION` for each
fresh process. A UUID identifies each service lifetime and dispatched request; the
request carries its generation. Another UUID identifies the raster worker operation.
The runtime supplies its State/preparation lifetime UUID and actual protocol transaction
number through a private thread property on the synchronous transaction worker. This
context propagates in `PreviewResult`, across queued publication, and through the
synchronous `changed` callback to the harness. No join uses timestamp proximity, process
addresses, session addresses or thread addresses. Preparation plus transaction number
is the compound transaction identity. A worker operation UUID does not claim OS-thread
identity. UUIDs identify instrumentation lifetimes, not loaded binaries or leases.

Events are successful pixel `eligible`, `store_entry`, `store_return`, progressive
`enqueue`, accepted image assignment `accepted`, the harness's first adequate-pixel
notification `adequate`, and accepted final completion `final`. Each carries invocation,
service, request, worker, preparation and transaction identities, generation, verified
source identity, requested dimensions, original-decode/cache-miss indication, tier and
decode outcome. `accepted` is recorded only inside the existing accepted image assignment;
stale/cancelled/timed-out results do not produce accepted pixels. `adequate` is recorded
inside the harness's existing first-adequate `changed` callback. `final` is after accepted
metadata application, before its notification, following the worker's storage and memory
cache work. Raw records must be retained and checked, never inferred from timer closeness.

A later runner must bind native binaries, installed provider resolution, runtime payloads
and protected-generation leases and validate actual loaded identities where available.
Input identities do not prove loading identities; missing loading evidence stays explicit.
Missing event identities are fatal even if loading identities have an explicit unavailable
status. Native correctness must cover target change during commit, cancellation, timeout,
shutdown, store failure, pixel/metadata ordering, cache availability at final completion
and session cleanup. None of those prerequisites has passed during this preparation.

Supporting evidence requires strict `store_entry < adequate < store_return` for the same
eligible request and compound transaction. Enqueue must precede accepted application,
which precedes first adequate notification; final completion must follow storage and
memory work with correct pixels and metadata. Equality at either store boundary is not
support. A complete valid schedule and passing correctness checks with at least one
supporting measured early observation yields **overlap observed**. A complete valid
schedule with none yields **overlap not observed in this population**. Missing identities,
malformed ordering, correctness/cleanup failure or an incomplete schedule yields
**Evidence insufficient**. Warm-ups cannot establish support. These outcomes establish
no performance gain, p95 improvement, visible Files rendering result or qualification
acceptance; these populations remain separate from historical timings.

## Offline acceptance

The [independent verifier](../../scripts/verify-preview-cache-publication.py) imports no
preparer or transformation implementation. Its own fixed literal allowlist reverses
allowed edits and compares complete source bytes, reconstructs the protocol, checks
complete package membership, inventories, diffs, anchors, tool snapshots, consumed
identities, seals and the zero-execution assessment. Its event-fixture checker defines
the future observation decision without executing a process.

[Focused synthetic tests](../../tests/test_preview_cache_publication.py) disable process
execution and cover anchors, duplicate publication, unrelated changes, inventory drift,
conflicting bindings, path collisions/overlap/symlinks, resealed tampering, blocked seals
and valid/invalid event populations. Verification is limited to these tests, one fresh
preparation, its independent offline verification, local-link checks, whitespace checks
and final diff review, following [proportional verification](../../CONTRIBUTING.md).
Unchanged historical verification is reused; no native build, suite, staging, workload
or recording runs. This document and the sealed package are the diagnostic protocol,
not a claim that native instrumentation compiles or execution is ready.
